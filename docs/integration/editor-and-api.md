## 2. Дизайн

### Стиль: один продукт, а не два сайта

Редактор использует токены из `frontend/src/shared/styles/tokens.css`
(`--surface`, `--ink`, `--line`, `--accent` и остальные), шрифт IBM Plex Sans, кнопки и поля
из `shared/ui`. Светлая и тёмная тема работают автоматически: редактор
не задаёт цвета напрямую, только через токены.

Отдельный вид допустим только внутри холста: сетка, заливка зон по цветам
из `categories.json → zone_types[].color`, линии маршрутов. Цвета зон
берутся из справочника, а не из кода редактора, — тогда легенда в редакторе,
в 3D и в отчёте совпадает.

**Почему не «отдельный инструмент со своим видом».** Пользователь проходит
шаги 1–6 в одном интерфейсе. Если на шаге 7 меняются шапка, кнопки и шрифт,
он решит, что его куда-то перебросило, и начнёт искать, как вернуться.
По НФТ интерфейс должен быть «понятен без инструкции» — смена визуального
языка посреди сценария это ломает.

### Технически: модуль того же React-проекта

Редактор переезжает в `frontend/src/features/planEditor/` и экспортирует
один компонент с интерфейсом `PlanEditorProps`. Визард монтирует его на шаге 7.

Почему не iframe:

| | Модуль того же проекта | Встроенное окно (iframe) |
|---|---|---|
| Тема, шрифты, токены | общие, ничего делать не нужно | копировать и синхронизировать вручную |
| Размер области | обычная вёрстка | передавать сообщениями `postMessage`, бороться со скроллом |
| Данные: план, справочник, состав роботов | обычные props | сериализация через `postMessage`, свой протокол |
| Сохранение и авторизация | одна сессия, один API-клиент | вторая сессия или проброс токена |
| Сборка и выкладка | одна | две, с совместимостью версий |

iframe имеет смысл, только если редактор должен жить отдельно от сайта. Такого
требования нет.

### Размер: рабочая область 1366×768

```
 56  шапка приложения
 48  полоса проекта
 52  степпер
┌─────────────────────────────────────────────────────────────────────────┐
│ 44  План объекта · статус · 2D/3D · Черновик из параметров · Сохранить  │  ← рисует визард
├────┬─────────────────────────────────────────────────────┬──────────────┤
│ 48 │                                                     │     264      │
│ ин │                  холст ≈ 1054 × 504                 │   свойства   │  ← рисует редактор
│ ст │                                                     │   выбранного │
│ ру │                                                     │   объекта    │
├────┴─────────────────────────────────────────────────────┴──────────────┤
 64  нижняя панель визарда: Назад / Сохранить черновик / Далее
```

- Визард отдаёт редактору `width` и `height` области и следит за ресайзом.
  Редактор не использует `100vh` и не рассчитывает на весь экран.
- **Визард рисует:** шапку, степпер, строку над холстом (название, статус
  сохранения, переключатель 2D/3D, «Сохранить план»), нижнюю панель.
- **Редактор рисует:** вертикальную рейку инструментов 48 px, холст, панель
  свойств 264 px. Своей шапки, своих кнопок «Сохранить»/«Назад» и своего
  меню у редактора нет.
- **Высота — резиновая, не фиксированная.** 548 px — это при окне
  браузера высотой 768. Но 1366×768 — разрешение экрана: вкладки, адресная
  строка и панель задач Windows забирают ещё ~100–130 px, и реальное окно
  страницы — около 1366×640. Тогда редактору остаётся ~330–400 px по высоте.
  Поэтому редактор тянется под `height`, который ему передали, и должен
  оставаться рабочим от **1054 × 360 px холста** (область редактора
  1366 × 400). Меньше — визард даёт странице прокрутиться, а не сжимает дальше.
- Всё, что не помещается в панель свойств, прокручивается внутри неё.

## 3. Интерфейс встраивания

```ts
// frontend/src/features/planEditor/types.ts
interface PlanEditorProps {
  value: TopologyConfig | null;          // null — плана ещё нет (черновик)
  onChange: (plan: TopologyConfig) => void; // каждое изменение; на сервер ходит визард
  context: {
    objectType: 'warehouse' | 'airport' | 'medical';
    areaSqm: number | null;              // из формы, для масштаба и проверок
    workingZoneIds: string[];            // из формы, id из categories.json → working_zones
    robots: { catalog_item_id; name; category_id; quantity }[]; // из состава оборудования
    minAisleWidthM: number | null;       // самый требовательный к проходу робот
  };
  categories: Categories;                // categories.json целиком
  width: number;                         // область, выделенная визардом, px
  height: number;
  readOnly?: boolean;                    // открыт старый снапшот версии
}
```

Правила:
- Редактор **не ходит на сервер**. Сохранение, статус, ошибки и конфликты — у визарда.
- Редактор **не хранит свой справочник**, берёт `categories` из props.
- Стартовое состояние: если `value === null`, визард предлагает «Черновик из
  параметров» — контур здания по площади, зоны по рабочим зонам из формы,
  зарядка, роботы у зарядки (`features/planEditor/autoLayout.ts`). Редактор
  может использовать его как основу, а не начинать с пустого холста.
- Сейчас на месте редактора стоит временный `PlanEditorStub` с тем же
  интерфейсом: показывает план, даёт выбрать зону и поменять название и
  категорию. Когда редактор Алексея готов, он встаёт на его место одной
  строкой в `StepTopology.tsx`.

## 4. Одна запись проекта на сервере

### Эндпоинты

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| `POST` | `/api/projects` | `ProjectCreateRequest` | `201 ProjectState` |
| `GET` | `/api/projects/{id}` | — | `200 ProjectState` |
| `PUT` | `/api/projects/{id}/input` | `InputSaveRequest` | `200 ProjectState` / `409` / `422` |
| `PUT` | `/api/projects/{id}/scene` | `SceneSaveRequest` | `200 ProjectState` (с `scene.warnings`) / `409` / `422` |
| `POST` | `/api/projects/{id}/scene/background` | multipart, поле `file` | `201 BackgroundUploadResponse` |
| `POST` | `/api/projects/{id}/versions` | — | снапшот `ProjectVersion` (шаг 8) |

Пути — из [api-routes.md](../../api-routes.md) (разделы 3, 6 и 11). Ручки
**разные, но запись одна**: обе части живут в одном проекте под одним
`project_id`, и обе ручки возвращают полное состояние записи — какие части
сохранены и чего ещё нет.

### Ответ — всегда целиком

```jsonc
// 200 после шага 2: параметры есть, плана нет — это нормальный черновик
{
  "project_id": "p-leningradka",
  "name": "Склад на Ленинградке",
  "object_type": "warehouse",
  "status": "draft",
  "revision": 4,
  "dictionary_version": 1,
  "input": { "state": "saved",   "revision": 4, "saved_at": "2026-09-22T10:15:00Z", "data": { "...": "ProjectInput" } },
  "scene": { "state": "missing", "revision": null, "saved_at": null, "based_on_input_revision": null,
             "data": null, "warnings": [] },
  "missing_parts":  ["scene"],    // чего ещё нет
  "blocking_parts": [],           // что мешает считать подбор и экономику: план не мешает
  "current_version": 3,
  "created_at": "...", "updated_at": "..."
}
```

После сохранения плана: `revision: 5`, `scene.state: "saved"`,
`scene.based_on_input_revision: 4`, `missing_parts: []`, в `scene.warnings` —
замечания по плану (см. раздел 9.3).

### Правила

1. **Связь по `project_id`.** Запись создаётся на `POST /api/projects` сразу при
   создании проекта. Всё дальнейшее досылается в неё по этому id — никаких
   отдельных «сессий редактора» и временных id.
2. **`revision` — один счётчик на весь проект.** Растёт на каждом успешном
   `PATCH`, какую бы часть ни сохраняли. Клиент отправляет последнюю
   известную `revision` в `base_revision`. Не совпала (сохранили из другой
   вкладки) — `409`, в ответе актуальный `ProjectState`, ничего не записано.
3. **План помнит, по каким параметрам нарисован** — `based_on_input_revision`.
   Если параметры сохранили после плана, сервер помечает план `stale`. План
   **не удаляется**: визард показывает «параметры менялись после плана» и
   предлагает проверить или пересобрать.
4. **Через день.** Пользователь открывает проект → `GET` → в ответе
   `input.state: saved`, `plan.state: missing`. Визард восстанавливает форму из
   `input.data`, степпер ведёт на первый непройденный шаг, редактор получает
   `value: null` и предлагает черновик из параметров. Нужен только `project_id`
   — он в адресе страницы.
5. **План без параметров не принимается** — `422`, код `input_required`.
   Параметры без плана принимаются всегда.
6. **Ошибки — `422` со списком `{path, code, message}`.** `message` на русском
   и показывается пользователю как есть. `path` указывает на поле:
   `input.params.area_sqm`, `plan.plan.zones[2].polygon`.
7. **`revision` ≠ версия.** `revision` — техническая ревизия черновика, их
   сотни. Версия (`ProjectVersion`, «версия 3» в интерфейсе) — снапшот, который
   пользователь сохраняет явно на шаге 8; по ней воспроизводится расчёт.
8. **Статус.** `draft`, пока нет расчёта. Сохранение параметров возвращает
   рассчитанный проект в `draft` — старый расчёт им больше не соответствует.
   Наличие плана на статус не влияет: шаг 7 необязательный.
9. **Гость в демо-режиме ничего не отправляет.** Его черновик живёт во
   вкладке и уходит на сервер одним `POST` + `PATCH` при регистрации.

## 5. Справочник: один на форму и редактор

**Проверка.** Форма держала свои списки в коде (`shared/mock/dictionaries.ts`) и
хранила в данных подписи: «Приёмка», «Фронтальные стеллажи». Типы зон
редактора (`ZoneType`: storage, operation, charging, restricted, transit) с
рабочими зонами формы никак не были связаны. `categories.json` Алексея в
репозитории нет — сверить было не с чем, поэтому общий справочник завёл
я, в `contracts/dictionaries/categories.json`. Форма уже переведена на него.

| Раздел `categories.json` | Где используется |
|---|---|
| `zone_types` (+ цвет) | редактор: тип зоны, заливка; 3D; отчёт |
| `working_zones` (+ `zone_type`) | форма: «Рабочие зоны»; редактор: `Zone.category_id` |
| `point_kinds` | редактор: `OperationPoint.kind` |
| `equipment_categories` (+ габарит) | каталог: тип решения; редактор: значок и размер робота |
| `storage_types`, `layout_constraints` | форма склада |
| `airport_zones`, `safety_requirements` | форма аэропорта |
| `facility_types`, `medical_cargo_categories`, `routes_and_elevators`, `sanitary_requirements`, `access_restrictions` | форма медучреждения |
| `operating_modes` | подсказки к полю «Режим работы» (по ТЗ это свободный текст) |
| `processes` | каталог |

Правила:
- В данных — только `id`. Подпись берётся из справочника при показе.
- Значение, вписанное пользователем вручную, уходит как `"custom:текст"`.
  Сервер принимает его, но подбор его не распознаёт — только показывает.
- **Связь формы и плана:** рабочая зона из формы (`receiving`) →
  `working_zones[].zone_type` (`operation`) → зона на плане с
  `category_id: "receiving"`. Поэтому редактор сразу знает, какие зоны
  пользователь уже назвал на шаге 2, а подбор — какие зоны нарисованы.
- Новое значение добавляется в JSON, код не меняется. `version` в файле
  растёт; сервер отдаёт `dictionary_version`, по которому проверял данные.

| границы объекта | `TopologyConfig.bounds` → `Bounds {origin, width_m, height_m}` | если не задано — считается по контуру стен |
| подложка (скан чертежа) | `TopologyConfig.background` → `SceneBackground` | **только ссылка**, см. 9.2 |
| названия у стен, точек, маршрутов, роботов | `name: str \| null` у `Wall`, `OperationPoint`, `Route`, `RobotPlacement` | у `Zone` имя было и раньше |
| количество мест у зарядки | `OperationPoint.capacity: int = 1` | для обычной точки — сколько роботов обслуживается одновременно |
| направление маршрута | `Route.direction: "two_way" \| "one_way"` | `one_way` — от первой точки ломаной к последней |
| привязка маршрута к точкам | `Route.from_point_id`, `Route.to_point_id` | ссылки на `OperationPoint.id` |
| вид робота | `RobotPlacement.category_id` | id из `equipment_categories`, когда модель не выбрана |
| поворот на старте | `RobotPlacement.start_rotation_deg: float = 0` | 0 — вдоль оси X |
| зарядка робота | `RobotPlacement.charging_point_id` | ссылка на точку с `kind: "charging"` |
| пустой `catalog_item_id` | `catalog_item_id: str = ""` | пусто разрешено и проверкой сервера |

### 9.2. Отдельная загрузка подложки — сделано

`POST /api/projects/{id}/scene/background` (multipart, поле `file`) → в ответе
`background_id`, `url`, размер в пикселях. В плане остаётся `SceneBackground`
со ссылкой, так что мегабайты при каждом сохранении не летают. Калибровка
(`scale_m_per_px`), смещение, поворот и прозрачность — в плане, а не в файле.
Ограничения: png, jpeg, pdf, до 25 МБ. Маршрут добавлен в `api-routes.md`, §11.1.

Загрузку делает визард (`uploadBackground` в `features/projectApi`), редактор
получает готовую ссылку в `value.background` и вызов `onUploadBackground(file)`
в props, если хочет свою кнопку.

### 9.3. Предупреждения с сервера — сделано

`ProjectState.scene.warnings: SceneWarning[]` в ответе на `PUT /scene`.
`SceneWarning {code, severity, message, target_kind, target_id}` — по
`target_id` редактор подсвечивает элемент.

Коды, которые сервер считает сейчас: `route_crosses_wall`,
`robot_in_restricted_zone`, `aisle_too_narrow` (маршрут ближе половины нужного
прохода к стене), `zone_outside_bounds`, `route_not_linked`,
`charging_capacity_exceeded`, `scene_area_differs_from_form` (площадь плана
расходится с формой больше чем на 20 %). `severity: error` означает, что план
сохранён, но симуляция по нему не пойдёт.

Эталонная реализация всех проверок лежит в
`frontend/src/features/projectApi/sceneChecks.ts` — геометрия там честная
(пересечение отрезков, точка в полигоне, расстояние до отрезка), бэкенду можно
переносить формулы оттуда. Редактор может дублировать их локально для
мгновенной подсветки, но истина — ответ сервера: те же замечания увидят
симуляция и отчёт.

### 9.4. Стоимость персонала — за одного сотрудника

В ТЗ написано «стоимость персонала в месяц», в контракте — «₽/мес **на одного
сотрудника**». Правильным считаем контракт, потому что экономика умножает:
`staff_count × staff_cost_per_month × 12`. Если бы это был фонд на всех, формула
завышала бы эффект в `staff_count` раз.

Что сделано в форме: подпись «Стоимость одного сотрудника», подсказка «на
одного человека, с налогами и взносами», и рядом считается контрольная сумма —
«на всех выходит N ₽ в месяц». Ошибку теперь видно сразу при вводе.

### 9.5. Один справочник — сведён, главные id английские

Главными оставляем **английские snake_case**: `receiving`, `storage`,
`stacker`, `amr`. Причина не вкусовая: значения из того же справочника уже
лежат в контрактах как enum (`ZoneType: storage/operation/charging/restricted/transit`,
`AcquisitionModel: purchase/leasing/raas`) и в каталоге через CPE. Транслит
(`zona_priemki`, `robot_shtabeler`) пришлось бы конвертировать в трёх местах.

Чтобы тебе ничего не переписывать: в `contracts/dictionaries/categories.json`
у значений появилось поле `aliases` с твоими названиями, и сервер **принимает
алиас на входе**, а в ответах и в данных возвращает главный id.

```jsonc
{ "id": "receiving", "label": "Приёмка", "zone_type": "operation",
  "aliases": ["zona_priemki", "priemka"] }
{ "id": "stacker", "label": "Робот-штабелёр",
  "aliases": ["robot_shtabeler", "shtabeler"] }
```

Алиасы проставлены для всех рабочих зон, типов зон, видов точек и категорий
техники (22 значения). **Пришли свой `categories.json`** — допишу недостающее
и добавлю алиасы к остальным; если в нём есть значения, которых у нас нет, они
переедут в общий файл, а не останутся отдельным списком.

### 9.6. Хватает ли данных симуляции — вопрос к Стасу

В план добавлено ровно то, что ты перечислил: направление маршрута, привязка
маршрута к точкам, стартовый поворот робота, его точка старта и зарядка, плюс
число мест у зарядки. Для `SimulationTimeline` этого, по-моему, достаточно:
робот стартует из `start_position` с `start_rotation_deg`, едет по маршрутам
между `from_point_id` и `to_point_id`, возвращается на `charging_point_id`,
а `capacity` ограничивает очередь на зарядке.

Чего в плане **нет** и что, возможно, понадобится Стасу — решаем вместе:
скорость движения внутри зон (ограничения), приоритет маршрутов, расписание
операций (сколько задач в час на точку). Скорость робота и производительность
пока берутся из каталога, а не из плана.
